# Running the backend in Docker

The backend can be built as one image and run the same way on any server. A deploy is "start this tag", and a rollback is "start the previous tag". **Nothing here changes the live server until the owner follows the steps below.** The existing `deploy.yml` (pm2) keeps working untouched.

Who does what: steps marked **[repo owner]** need the owner of the backend repository (the main owner is only a collaborator there). Steps marked **[server]** need someone who can log in to the server. Steps marked **[either]** can be done by whoever has the access.

## 0. The one rule: only ONE process runs the background jobs

The server starts work on its own, with no user behind it. **While two processes share the database (the old pm2 server and a Docker container), exactly one of them may run it: the old server, until the cutover.** The container is started with `BACKGROUND_JOBS=off` for the whole test period, and switched on only in the cutover (section 7).

| Job | What it does (from the code) | Why two copies are a problem |
|---|---|---|
| Sweep of expired forms (at start, then every 5 minutes) | sets `status` from `published` to `closed` on forms past their close date. Database only | harmless twice |
| **Trash purge** (at start, then every 5 minutes) | **permanently deletes** forms and responses that have been in Trash for 30 days: their database records **and their files from the uploads folder of that process**. At most 50 forms and 50 responses per run | the container deletes the record for good, but only the files it has: the old server's copy of those files stays behind as orphans |
| Storage reconcile (10 minutes after start, then daily) | recomputes each user's `storageUsedBytes` **from the database** and writes only that one counter when it differs. It **never reads the disk, never deletes a file and never creates, changes or deletes a record other than that counter** (`services/storage.service.ts`, `reconcileUser`). A disagreement between disk and database therefore changes nothing | harmless twice (a run skips a user whose counter moves while it measures) |
| Report-queue recovery (at start) | puts reports stuck in `processing` for 15 minutes back to `queued`, then **starts generating every queued report in that process**, writing the PDF or CSV under that process's uploads folder | a report generated by the container exists only in the container's volume; the old server cannot serve it |
| Index sync of one collection (at start) | makes the `EmailVerification` indexes match this version's schema (can drop a stale index) | idempotent, but it changes the shared database from a different code version |

`BACKGROUND_JOBS=off` (also `false`, `0`, `no`) switches **all five** off. Default is on, so a server that does not set it behaves exactly as before. The container logs `Background jobs are OFF (BACKGROUND_JOBS)` or `Background jobs are ON` at start: check that line every time.

**Other things that write to the database without a user request** (so you know what is *not* covered by the switch):
- **MongoDB itself** deletes expired documents on a timer, whichever process is running: `EmailVerification` and `Invitation` (`purgeAt`), `RateLimitBucket` (`expiresAt`) and `RespondentLink` (30 days after `expiresAt`).
- **Mongoose creates missing indexes** for every model when a process connects (default `autoIndex`). A container built from a newer commit than the running server can add indexes to the shared database.
- **The report queue is also started by a request** (a user asks for a report or an export). The next process to look claims the **oldest queued report in the whole database**, wherever it was asked for. So **never ask for a report from the test container while it uses the live database**: it could pick up a report requested on the live server and write its file where the live server cannot see it.
- Everything else that writes (forms, responses, uploads, sessions, rate-limit counters, notifications, emails) only runs because a user, a browser or a script called the API.

## 1. What the image is

| | |
|---|---|
| Base | `node:20-bookworm-slim` (the major version in `.nvmrc` and CI; `-slim`, not alpine, so the image matches the platform the dependencies are tested on; there is no browser or native module) |
| User | `node` (**uid 1000, gid 1000**), never root. `tini` is PID 1, so `docker stop` is a graceful stop |
| Code | `/app`, owned by root, read-only to the app |
| Data | `/data` is a **volume**; the working directory is `/data`, and the app writes only there: `/data/uploads` (uploaded files, `response.json`), `/data/uploads/reports` (report PDFs and CSVs), `/data/uploads/exports` (workspace exports) |
| Port | 5000 inside the container (`PORT`) |
| Health | `GET /api/health` answers 200 `{ "commit": "<7 characters>" }`; `GET /` answers the same commit (the deploy check greps it; the admin Releases page reads it) |
| Version | the build writes `dist/version.json` from `GIT_SHA` and `BUILD_TIME`, the same file and field names the pm2 deploy writes, and `dist/audit.json` (the dependency-audit count System Health shows) |
| Logs | stdout only (no log files); Docker rotates them (`max-size 10m`, 5 files) |
| Time zone | `TZ=UTC` (change with the `TZ` variable) |
| Secrets | none in the image. Settings come from the env file at run time; the Firebase key is mounted read-only |

The container **refuses to start in production** when one of these is missing, and says which one by name (never its value): `JWT_SECRET`, `MONGODB_URI`, `PROXY_SHARED_SECRET`, and the Firebase key file. The mail settings and `APP_URL` are **not** required: the code has a default for each (`APP_URL` https://beginso.com, `SMTP_HOST` email.toowix.com, no login, sender no-reply@beginso.com), the live server's `.env` sets none of them, and the container prints a note naming the ones that are not set. This check lives in `docker/preflight.js` and runs only in the container.

## 3. Prepare the server  **[server]**

1. **Install Docker** (Docker's own apt repository, "Install using the apt repository" in the Docker documentation for your Ubuntu version), then create a deploy user that is **not root** and let it use Docker without `sudo`:
   ```
   sudo adduser --disabled-password --gecos "" deploy
   sudo usermod -aG docker deploy
   ```
   Everyday commands are then run as `deploy`. (Membership of the `docker` group is equivalent to root on this machine: give it only to the deploy user.)
2. **Make the folders** (as `deploy`):
   ```
   sudo mkdir -p /opt/beginso-backend/data /opt/beginso-backend/data-test /opt/beginso-backend/secrets
   sudo chown -R deploy:deploy /opt/beginso-backend
   sudo chown -R 1000:1000 /opt/beginso-backend/data /opt/beginso-backend/data-test   # the `node` user inside the image is uid 1000
   chmod 700 /opt/beginso-backend/secrets
   ```
   `data` is the real volume (filled at the cutover). `data-test` is a scratch folder for the test container: it is thrown away afterwards.
3. **The env file.** Create `/opt/beginso-backend/.env` from `.env.example` (same names, the values the live server already uses; copy them from the current `.env` of the pm2 app, do not retype). Then:
   ```
   chmod 600 /opt/beginso-backend/.env      # readable only by the deploy user
   ```
   Set `TRUST_PROXY_HOPS` to the number of proxies **in front of the container** (nginx only = 1; Cloudflare plus nginx = 2). Leave `UPLOAD_DIR` unset: the image sets `/data/uploads`. **Do not put `BACKGROUND_JOBS` in `.env`**: it is set in `.deploy/env` (step 5) so that one line decides.
4. **The Firebase key file: who owns it and what to run.** The container runs as **uid 1000, gid 1000**. The file is mounted into the container as it is on the host, so **the host file's owner and mode decide whether the container can read it**:
   ```
   sudo cp /root/Onboarding-backend/dist/config/firebase/serviceAccountKey.json /opt/beginso-backend/secrets/serviceAccountKey.json
   sudo chown 1000:$(id -g deploy) /opt/beginso-backend/secrets/serviceAccountKey.json
   sudo chmod 440 /opt/beginso-backend/secrets/serviceAccountKey.json
   ls -ln /opt/beginso-backend/secrets/serviceAccountKey.json      # expect: -r--r----- 1 1000 <deploy gid> ...
   ```
   (uid 1000 reads it as owner; the deploy user reads it through the group; nobody else can.) The file must exist **before** the first start. If the errors below appear, the logs of the container (`docker logs beginso-api`) say, by name:

   | Mistake | What the log says |
   |---|---|
   | the host file does not exist (Docker then creates an **empty folder** with that name) | `FATAL: Refusing to start:` `the Firebase key path is a FOLDER, not a file: the host path in FIREBASE_KEY_PATH did not exist when the container started ...`. Fix: `sudo rmdir /opt/beginso-backend/secrets/serviceAccountKey.json`, copy the file, start again |
   | the file exists but uid 1000 may not read it (wrong owner or mode) | `the Firebase key file exists but this container user (uid 1000) cannot read it: on the host run chown 1000:<group> and chmod 440 on the file` |
   | `FIREBASE_KEY_PATH` points at nothing | `the Firebase service-account key file is missing: mount it read-only at dist/config/firebase/serviceAccountKey.json (FIREBASE_KEY_PATH)` |
   | the file is there but is not valid JSON or is the wrong key | the app prints `Firebase serviceAccountKey.json is missing. Refusing to start in production.` (the app uses the same message for every failure to load the file) |

   With `restart: unless-stopped` a container that refuses to start is restarted over and over: stop it with `docker rm -f beginso-api` while you fix the file.
5. **Tell the deploy script where things are**, in `/opt/beginso-backend/.deploy/env` (create the folder):
   ```
   UPLOADS_PATH=/opt/beginso-backend/data-test
   FIREBASE_KEY_PATH=/opt/beginso-backend/secrets/serviceAccountKey.json
   HOST_PORT=5001
   BIND_ADDRESS=127.0.0.1
   BACKGROUND_JOBS=off
   ```
   `HOST_PORT=5001` is a **spare port**, so the container runs next to the current backend (port 5000), and `BIND_ADDRESS=127.0.0.1` keeps it reachable only from the VM itself. `BACKGROUND_JOBS=off` and `UPLOADS_PATH=.../data-test` are the **test settings**; the cutover (section 7) changes all four.

**How the container is reached.** `docker-compose.prod.yml` publishes one port, `"${BIND_ADDRESS:-127.0.0.1}:${HOST_PORT:-5000}:5000"`. By default it is the loopback, so a test container can only be reached from the VM itself. At the cutover `.deploy/env` sets `BIND_ADDRESS=0.0.0.0` and `HOST_PORT=5000`, which is **the same exposure the pm2 backend has today** (all addresses, port 5000), and nothing wider. The firewall being inactive is how the VM was set up and is not changed here; if you want the backend reachable only from your forwarder, that is a separate firewall decision.

## 4. Get the image  **[repo owner] once, then [either]**

The image comes from GitHub Container Registry, built by the workflow **Publish Docker Image** (manual: Actions → Publish Docker Image → Run workflow). Before its first run, the **repo owner** must:

1. allow the workflow to write packages: Settings → Actions → General → Workflow permissions → "Read and write permissions";
2. after the first publish, open Packages → `beginso-backend` → Package settings, link it to this repository and keep it **private**;
3. give the server a way to pull a private image: create a personal access token with only `read:packages` and run `docker login ghcr.io -u <user>` once as `deploy` (the token is stored by Docker, not in this repository).

Tags: `sha-<7 characters of the commit>` (use this one for deploys) and `main`. Never deploy `latest`.

Without a registry you can build on the server instead: `docker build --build-arg GIT_SHA=$(git rev-parse HEAD) -t beginso-backend:sha-$(git rev-parse --short=7 HEAD) .` and deploy that tag.

**During the cutover window, `deploy.yml` must not run.** A push to `main` runs it, and its last steps are `pm2 restart onboarding-backend`: that would **start the old server again** next to the container (two processes running the timers, the old one with the old uploads). The **repo owner** disables it before section 7 (Actions → Deploy Backend → "…" → Disable workflow) and enables it again only after the Docker deployment is settled, or after a rollback. (Once the automatic Docker deploy is switched on, section 11, `deploy.yml` skips itself and no longer needs to be disabled.)

## 4b. Other containers on the VM  **[server]**

The VM already runs other Docker containers that must not be affected. This setup is built to never touch them, and you can check that before every cutover.

**What is ours, and only ours**

| Object | Name | Label |
|---|---|---|
| Compose project | `beginso-api` (laptop: `beginso-api-dev`), fixed in the file, never taken from the folder name | |
| Container | `beginso-api` (write-check container: `beginso-api-write-test`) | `com.beginso.app=api` |
| Network | `beginso-api`, created and removed with the project | `com.beginso.app=api` |
| Image | the registry name `ghcr.io/<owner>/beginso-backend:sha-<commit>` | `com.beginso.app=api`, built into the image |
| Volumes | none on the server: the data is a folder, `/opt/beginso-backend/data` (a bind mount) | |

**Rules, enforced by `scripts/check-docker-hygiene.sh` (it runs in CI and fails the build when one is broken)**

- Nothing runs `docker system prune`, `docker image prune -a`, `docker volume prune`, `docker network prune` or any other prune without the label filter `com.beginso.app=api`. Nothing stops, kills or removes "all containers". Nothing restarts the Docker daemon.
- Cleanup is `./scripts/deploy-docker.sh cleanup` (also run after every successful deploy). It removes only **stopped containers and images that carry our label**, keeps the **newest 5 image tags** and never the current or the previous one. Run it with `--dry-run` first to see the list.
- Every published port is bound to `127.0.0.1` by default; the address comes only from the variable `BIND_ADDRESS` and the port from `HOST_PORT` (below). The deploy checks the port **before it starts anything**: when something else holds it, it stops with a message and changes nothing.
- **Docker must not be reinstalled, upgraded or restarted for this.** Restarting the daemon interrupts every container on the machine, and a reinstall can replace the daemon's settings. If Docker itself needs a change, that is a separate decision with whoever owns the other containers, not a step of this runbook.
- To stop ours: `docker rm -f beginso-api` (it names exactly our container and nothing else; `docker compose down` is not used because the compose file asks for `BACKEND_IMAGE` even to stop). Never `docker stop $(docker ps -q)`.

**Check before the first start and before the cutover (changes nothing)**

```
cd /opt/beginso-backend
./scripts/deploy-docker.sh check
```

It lists every container with its image, ports and status; every listening TCP port; whether `HOST_PORT` is free (or held by our own container); and the free memory, with a warning when less than the container limit (768 MB) plus 512 MB is available. The same by hand:

```
docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}\t{{.Status}}'      # names and ports in use, ours is beginso-api
docker ps -a --filter name=beginso-api                                              # our name is not taken by anything else
sudo ss -ltnp                                                                       # who listens on which port
docker network ls ; docker volume ls                                                # nothing of ours exists yet
free -h ; docker stats --no-stream                                                  # memory left, and what the other containers use
```

If the port is taken the deploy ends with `PORT <n> IS ALREADY IN USE by something that is not beginso-api` and exit code 3. Choose another port: put `HOST_PORT=<free port>` in `/opt/beginso-backend/.deploy/env`, point the proxy at it, run again. Never stop the other container to make room. If the memory warning appears, do not cut over until the other containers' usage is understood.

**Our ports** (on `127.0.0.1` unless `BIND_ADDRESS` says otherwise; each set by one variable)

| Port | Variable | Used by |
|---|---|---|
| 5000 | `HOST_PORT` | the server container (the first test container uses 5001); the address is `BIND_ADDRESS` (default `127.0.0.1`, `0.0.0.0` on this VM after the cutover) |
| 5002 | `WRITE_TEST_PORT` | the write-check container (section 8) |
| 5000 | `HOST_PORT` | `docker compose up` on a laptop (`docker-compose.yml`) |

## 5. Start the test container (background jobs OFF)  **[server]**

The test container uses the **live database** but an **empty scratch uploads folder** and **no background jobs**. So it must only be used to **look**:

- **Allowed:** `GET /api/health`, signing in, opening the forms list, the responses list and a response, opening the public form page.
- **Not allowed:** uploading anything, submitting a response with a file, asking for a report or an export, creating or editing forms or responses. Every file the container writes exists only in `data-test`, while its database record is shared with the live server, which would then have a record without a file. A report request is worse: see the section 0 note on the report queue.

For the write checks (uploads, reports, exports) use a **separate test database** (section 8), never the live one.

```
cd /opt/beginso-backend
# copy docker-compose.prod.yml and scripts/ here from the repository (the deploy workflow does this for you)
./scripts/deploy-docker.sh check          # section 4b: other containers, ports, free memory; changes nothing
./scripts/deploy-docker.sh deploy ghcr.io/<owner>/beginso-backend:sha-abc1234
docker logs beginso-api 2>&1 | grep "Background jobs"          # must say: Background jobs are OFF
curl http://127.0.0.1:5001/api/health                              # {"success":true,...,"commit":"abc1234"}
./scripts/deploy-docker.sh status
```

The container listens only on `127.0.0.1:5001`; the old backend on 5000 is untouched and **keeps running the timers**. Look around **from the VM** (`curl http://127.0.0.1:5001/...`) or from your own machine through an SSH tunnel (`ssh -L 5001:127.0.0.1:5001 root@192.168.33.47`, then `http://localhost:5001`), or point a test copy of the frontend at the tunnel. The script puts the previous tag back by itself if the health check or the commit check fails (on a first deploy there is none: the container just stays unhealthy; read section 10).

## 6. Resources: measure the old server, then set the limits  **[server]**

Read what the live process uses now (pm2 runs as root, so use `sudo` if pm2 is root's):

```
sudo pm2 describe onboarding-backend | grep -E "memory|cpu|uptime|restarts"   # current memory and CPU
sudo pm2 monit                                                                # live graph; q to quit
sudo pm2 jlist | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{for(const p of JSON.parse(s).filter(p=>p.name==='onboarding-backend'))console.log('RSS MB',Math.round(p.monit.memory/1048576),'CPU %',p.monit.cpu)})"
```

One reading is not enough. For a week, record one line a minute and look at the **peak**:

```
sudo crontab -e      # add:
* * * * * pm2 jlist | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const p=JSON.parse(s).find(p=>p.name==='onboarding-backend');console.log(new Date().toISOString(),Math.round(p.monit.memory/1048576),p.monit.cpu)})" >> /var/log/beginso-pm2-usage.log
sort -k2 -n /var/log/beginso-pm2-usage.log | tail -1      # the line with the peak memory (MB)
sort -k3 -n /var/log/beginso-pm2-usage.log | tail -1      # the line with the peak CPU (%, of ONE core)
```

**Setting the limits, leaving 50 percent headroom:** the limit is the observed peak plus 50 percent.

| | Formula | Example |
|---|---|---|
| `mem_limit` | peak memory (MB) × 1.5, never below 768 | peak 410 MB → 615 → set `768m` |
| `cpus` | peak CPU (% of one core) ÷ 100 × 1.5, never below 1.0 | peak 80 % → 1.2 → set `1.5` |

Change the two lines in `docker-compose.prod.yml` (the default there, `768m` and `1.5`, is sized for this VM: about 1.1 GB free beside the other containers, the live backend at about 120 MB), redeploy the same tag, and watch `docker stats --no-stream beginso-api` for the first week. Reports run inside this process (two at a time, `REPORT_CONCURRENCY`), so a limit set from a quiet week can be too low on a day with many exports: if the container is killed for memory (`docker inspect beginso-api --format '{{.State.OOMKilled}}'` says `true`), raise it by 50 percent.

## 7. The real cutover  **[server]**, with the repo owner's `deploy.yml` disabled (section 4)

Do it at a quiet time. The site is down from step 2 until step 7 (a few minutes, mostly the copy). There is **no proxy to switch** on this VM (section 3b): the container takes over port 5000 itself, so whatever forwards to the VM keeps working unchanged. Run the commands as `deploy` (`sudo` where shown). Replace the image tag.

1. **Say it is starting** and check the old server is the live one: `curl -s http://127.0.0.1:5000/` shows the commit; `docker logs beginso-api 2>&1 | grep "Background jobs"` still says OFF.
2. **Stop the old server (stops its timers and its writes):**
   ```
   sudo pm2 stop onboarding-backend
   ```
3. **Stop the test container:** `cd /opt/beginso-backend && docker rm -f beginso-api`
4. **Final copy of the uploads into the volume** (copy, never move; only new and changed files travel the second time):
   ```
   sudo rsync -a --info=progress2 /root/Onboarding-backend/uploads/ /opt/beginso-backend/data/uploads/
   sudo chown -R 1000:1000 /opt/beginso-backend/data
   ```
5. **Verify counts and checksums. Both must match exactly; if not, STOP and go to section 9 (rollback), do not continue:**
   ```
   sudo find /root/Onboarding-backend/uploads -type f | wc -l
   sudo find /opt/beginso-backend/data/uploads -type f | wc -l
   ( cd /root/Onboarding-backend/uploads && sudo find . -type f -print0 | sort -z | xargs -0 sudo sha256sum ) > /tmp/uploads-before.sha
   ( cd /opt/beginso-backend/data/uploads && sudo find . -type f -print0 | sort -z | xargs -0 sudo sha256sum ) > /tmp/uploads-after.sha
   diff /tmp/uploads-before.sha /tmp/uploads-after.sha && echo "COPY VERIFIED"
   ```
6. **Point the deploy script at the real volume, the live port and address, and switch the jobs ON** (this is the step that makes the container the one process running the timers and the one answering on port 5000):
   ```
   sed -i 's#^UPLOADS_PATH=.*#UPLOADS_PATH=/opt/beginso-backend/data#; s#^BACKGROUND_JOBS=.*#BACKGROUND_JOBS=on#; s#^HOST_PORT=.*#HOST_PORT=5000#; s#^BIND_ADDRESS=.*#BIND_ADDRESS=0.0.0.0#' /opt/beginso-backend/.deploy/env
   grep -E "UPLOADS_PATH|BACKGROUND_JOBS|HOST_PORT|BIND_ADDRESS" /opt/beginso-backend/.deploy/env      # must show data (not data-test), on, 5000 and 0.0.0.0
   ```
7. **Start the container:**
   ```
   cd /opt/beginso-backend && ./scripts/deploy-docker.sh deploy ghcr.io/<owner>/beginso-backend:sha-abc1234
   docker logs beginso-api 2>&1 | grep "Background jobs"          # must say: Background jobs are ON
   curl -s http://127.0.0.1:5000/ | grep abc1234                      # the live commit, from the VM
   ```
   Port 5000 is free at this point because pm2 was stopped in step 2; if it is not, the script stops with "PORT 5000 IS ALREADY IN USE" and changes nothing.
   ```
   ```
8. **Look from outside the VM:** from another machine `curl http://192.168.33.47:5000/` and `curl https://api.beginso.com/` must both report the new commit; open a form and an existing uploaded file (it must download and match its checksum).
9. **Nothing to switch.** The address and port are the ones the pm2 backend had, so the forwarder and the frontend need no change. (If step 8 does not answer from outside but does from the VM, `BIND_ADDRESS` is still `127.0.0.1`: fix step 6, redeploy.)
10. **Check the live site:** sign in, open a form, submit a test response with a file, open the file, export a PDF. Watch `docker logs -f beginso-api` for errors for ten minutes.
11. **Leave pm2 stopped, not deleted** (`pm2 stop`, never `pm2 delete`), and keep `/root/Onboarding-backend/uploads` untouched for a few weeks: they are the way back. Do **not** run `pm2 start` while the container is live.

## 8. Write checks on a separate test database  **[server]**

Do this **before** the cutover, with a second container on a **throwaway database** (a different database name on the same cluster, for example `.../beginso_docker_test`), a scratch uploads folder, and its own port. Never against the live database. The test frontend must point at this container and sign in with an account created in the test database.

```
mkdir -p /tmp/dtest && sudo chown 1000:1000 /tmp/dtest
docker run -d --label com.beginso.app=api --name beginso-api-write-test -p 127.0.0.1:${WRITE_TEST_PORT:-5002}:5000 -v /tmp/dtest:/data \
  --env-file /opt/beginso-backend/.env \
  -e MONGODB_URI='<the SAME cluster, database name beginso_docker_test>' \
  -e BACKGROUND_JOBS=off \
  -v /opt/beginso-backend/secrets/serviceAccountKey.json:/app/dist/config/firebase/serviceAccountKey.json:ro \
  ghcr.io/<owner>/beginso-backend:sha-abc1234
```

The manual checklist (tick each):

1. **Upload a file:** in the test frontend create a form with a file question, open its public page and submit a response with a small file. Find it in the volume: `sudo find /tmp/dtest/uploads -type f -newer /opt/beginso-backend/.env` (it is under `<user id>/<form id>/responses/<response id>/`). Note its checksum: `sudo sha256sum <that path>`.
2. **Recreate the container:** `docker rm -f beginso-api-write-test`, then run the same `docker run` command again.
3. **Download the same file through the API:** in the test frontend open that response and download the file (or `GET /api/responses/<response id>/file/<file id>` with the session). `sha256sum` of the download must equal the checksum from step 1.
4. **Run one report:** Exports → a CSV, then a PDF of those responses. Both must reach `Completed`. Find them: `sudo ls -l /tmp/dtest/uploads/reports/`.
5. **Run one export:** Settings → export workspace data. Find it: `sudo ls -l /tmp/dtest/uploads/exports/`.
6. **Stop it gracefully:** `time docker stop beginso-api-write-test`; `docker inspect beginso-api-write-test --format '{{.State.ExitCode}}'` says `0`, and the stop took well under 30 seconds.
7. **Confirm from outside that the container's port is closed** (below).
8. Clean up: `docker rm -f beginso-api-write-test; sudo rm -rf /tmp/dtest`, and drop the `beginso_docker_test` database.

**Confirm from outside that port 5001 (and 5002) is closed.** From **another machine** (a laptop, not the server):

```
nc -vz -w 5 <server-public-ip> 5001       # must fail (timed out or refused)
curl -m 5 http://<server-public-ip>:5001/api/health      # must not answer
```

On the server, the listener must be on the loopback only:

```
sudo ss -ltnp | grep -E ":500[12]"        # during the test phase: must show 127.0.0.1:5001 , never 0.0.0.0:5001 or *:5001
docker port beginso-api               # test phase: 5000/tcp -> 127.0.0.1:5001   (after the cutover: 0.0.0.0:5000, on purpose, like the pm2 backend)
```

Do not rely on `ufw` for this: Docker writes its own firewall rules for published ports and they bypass `ufw`. Only the `127.0.0.1` address in the port mapping keeps the port private. After the cutover port 5000 is public to the network on purpose, exactly as the pm2 backend is today.

## 9. Rollback to the old server  **[server]**

Use it when step 5 of the cutover does not match, when the live checks fail, or later when the old way is wanted back. The container may have received **new uploads, reports and exports since the cutover**: they exist only in the volume, so they are copied back **before** pm2 starts. The copy is "only newer files": it never overwrites a file the old folder has newer, and never deletes anything.

1. **Stop the container (stops its timers and its writes):**
   ```
   cd /opt/beginso-backend && docker rm -f beginso-api
   ```
2. **Copy the volume's contents back into the old uploads folder, only newer files, keeping the old folder's owner:**
   ```
   sudo rsync -rlt --update --no-owner --no-group --info=progress2 /opt/beginso-backend/data/uploads/ /root/Onboarding-backend/uploads/
   ```
3. **Verify: every file in the volume now exists, identical, in the old folder** (the command prints `FAILED` for a mismatch and nothing else when all is well):
   ```
   ( cd /opt/beginso-backend/data/uploads && sudo find . -type f -print0 | sort -z | xargs -0 sudo sha256sum ) > /tmp/volume.sha
   ( cd /root/Onboarding-backend/uploads && sudo sha256sum -c /tmp/volume.sha --quiet ) && echo "ROLLBACK COPY VERIFIED"
   ```
   If a line says `FAILED`, that file is **newer on the old side** (kept on purpose by `--update`): compare the two by hand before going on.
4. **Start the old server (its timers start again):**
   ```
   sudo pm2 start onboarding-backend
   sleep 10 && curl -s http://127.0.0.1:5000/             # the commit of the old build
   ```
5. **Nothing to switch back.** pm2 takes port 5000 again, the address the forwarder already uses; check `curl https://api.beginso.com/` reports the old build's commit.
6. **Check:** sign in, open a form, open an uploaded file, and one that was uploaded while the container was live.
7. Keep the volume (`/opt/beginso-backend/data`) as it is. Tell the repo owner to enable `deploy.yml` again only when the old way is meant to stay.

Rolling back **between Docker tags** (a bad image, same uploads): `./scripts/deploy-docker.sh rollback`. It starts the previous tag, checks health and the commit, and does not touch the uploads.

## 10. Day to day, and when the health check fails

| Task | Command |
|---|---|
| Logs (live) | `docker logs -f --tail 200 beginso-api` |
| Is it healthy? | `docker ps` (the Status column says `healthy`), or `curl http://127.0.0.1:5001/api/health` |
| Update | publish a new image, then `./scripts/deploy-docker.sh deploy ghcr.io/<owner>/beginso-backend:sha-<new>` |
| Roll back an image | `./scripts/deploy-docker.sh rollback` |
| What is running | `./scripts/deploy-docker.sh status` |
| Other containers, ports, free memory | `./scripts/deploy-docker.sh check` (changes nothing; section 4b) |
| Remove our old images | `./scripts/deploy-docker.sh cleanup --dry-run`, then `./scripts/deploy-docker.sh cleanup` (only our label, keeps the newest 5 tags; also runs after each deploy) |
| Back up the uploads | `tar -czf uploads-$(date +%F).tar.gz -C /opt/beginso-backend/data uploads` (or rsync the folder to another machine); a database backup is separate (MongoDB Atlas) |
| Change a setting | edit `/opt/beginso-backend/.env`, then redeploy the same tag (`deploy` with the current tag restarts it) |

A deploy is a **few seconds** of refused connections: one container on one port means the old container stops before the new one starts. Zero downtime (two containers behind the proxy) is **not recommended**: both would run the timers (section 0). Use stop-then-start.

**If the health check fails:**

1. `docker logs --tail 200 beginso-api`. The first lines say what the container refused: a **missing setting is named** (`JWT_SECRET is missing (...)`), the Firebase key is named (see the table in section 3), a database that cannot be reached shows "MongoDB connection attempt N failed" (it retries 10 times, 5 seconds apart).
2. The deploy script has already started the previous tag again. Confirm with `./scripts/deploy-docker.sh status`.
3. Missing setting: add it to `.env`, redeploy. Database: check the Atlas IP allow-list includes this server. Permission error writing `/data`: `sudo chown -R 1000:1000 /opt/beginso-backend/data`.
4. Still stuck: `./scripts/deploy-docker.sh rollback`, or the full rollback to pm2 (section 9).

## 11. Automatic Docker deploy (OFF by default)  **[repo owner]**

After a push to `main` the whole Docker deploy can run by itself. It is **off** until the repository variable `DOCKER_DEPLOY_ENABLED` is exactly `true`. Nothing is enabled by merging the workflows.

```
push to main -> ci (green) -> Publish Docker Image (sha-<commit>) -> Deploy Backend (Docker) on the VM
```

| `DOCKER_DEPLOY_ENABLED` | `Deploy Backend` (pm2, `deploy.yml`) | `Publish Docker Image` (after ci) | `Deploy Backend (Docker)` |
|---|---|---|---|
| not set, empty, `false`, anything but `true` | **runs** (as it always did) | does not run by itself | does not run, not even by hand |
| `true` | skips itself | runs | **runs** |

The two deploys can never run together: the pm2 job has the opposite condition, and both jobs share the concurrency group `backend-deploy`, so even at the moment the variable is flipped they queue one behind the other. A **manual** run of `Publish Docker Image` is allowed whatever the variable says: it only builds and pushes an image and touches no server (the test container of section 5 needs one before the switch is on).

**The runner is the VM.** `deploy.yml` shows it: its `self-hosted` job copies into `/root/Onboarding-backend`, runs `pm2 restart` and curls `127.0.0.1:5000`, which only works on the machine that runs the app. The Docker deploy job runs on the same runner.

### What the Docker deploy does

1. Pulls `ghcr.io/<owner>/beginso-backend:sha-<commit>` (the image the publish step built for exactly the commit ci passed; there is no `latest`).
2. Writes down the tag now running as the **previous** one (`.deploy/previous` on the VM; the previous image stays on the disk).
3. Starts the new tag with `docker-compose.prod.yml`.
4. Waits for the health check (90 s), then checks that `GET /` reports **this commit**.
5. If either check fails, or anything else goes wrong: **starts the previous tag again** and fails the job: red, with an error annotation and a summary that says what was wanted. A first deploy with no previous tag just stays red.

### What stays on the VM and what GitHub holds

- On the VM only: the env file (`/opt/beginso-backend/.env`, `chmod 600`), the Firebase key, the uploads volume, `.deploy/`. The workflow copies only `docker-compose.prod.yml` and the two scripts into `/opt/beginso-backend` and never reads or prints the env file.
- GitHub holds **no secret for this**: the job's own `GITHUB_TOKEN` (permission `packages: read`, valid for the job) logs in to the registry to pull the image, and the job logs out at the end. No personal access token is stored. (The package must be linked to this repository, section 4.)

### Which runner user needs Docker, and the risk

The user the Actions runner service runs as. Find it on the VM: `ps -o user= -C Runner.Listener` (or `systemctl status 'actions.runner.*'`). From `deploy.yml` (it writes into `/root/Onboarding-backend` and runs `pm2`) it is almost certainly **root**: then it needs nothing added. If it is **not** root, it must be allowed to use Docker: `sudo usermod -aG docker <runner-user>`, then restart the runner service.

**The risk:** membership of the `docker` group is **root-equivalent on that machine**: whoever can run a job on this runner (anyone who can push a workflow to this repository, or approve a pull request that runs there) can start a container that mounts the whole disk and become root. That is why (a) the Docker deploy job runs only from `main` after ci, (b) it uses the `production` Environment, where **required reviewers** can be added, and (c) `ci` and the pull-request checks run on GitHub's own runners, never on the VM.

### Switching it on, and where it fits in the cutover

Only after the **manual cutover (section 7) has worked and settled** (the container is the live backend, the uploads are in the volume, `BACKGROUND_JOBS` is on). Never before: switching it on while pm2 is the live server would deploy a container next to it.

1. **[repo owner]** Create the Environment: Settings → Environments → New environment → `production`. Add **Required reviewers** (yourself) if you want every deploy to wait for a click.
2. **[server]** Check the runner user and Docker (above), and that `/opt/beginso-backend/.deploy/env` has `UPLOADS_PATH=/opt/beginso-backend/data`, `BACKGROUND_JOBS=on`, `HOST_PORT=5000` and `BIND_ADDRESS=0.0.0.0` (section 3b).
3. **[repo owner]** Set the variable: Settings → Secrets and variables → Actions → Variables → New repository variable → name `DOCKER_DEPLOY_ENABLED`, value `true`.
4. Push a small change to `main` (or run `Deploy Backend (Docker)` by hand with the tag that is already running) and watch the run: ci, Publish Docker Image, Deploy Backend (Docker). Check the site, `docker ps`, and `curl http://127.0.0.1:<port>/`.

**By hand** (Actions → Deploy Backend (Docker) → Run workflow, only while the variable is `true`): `deploy` with a **tag** (`sha-abc1234`, or a full image name) deploys any tag, **an earlier one included: that is the rollback to a tag**. `rollback` starts the tag that ran before the current one.

### Going back to pm2 by clearing the variable

Clearing the variable stops the **automatic** Docker deploys and makes `deploy.yml` run again on the next push. It does **not** stop the container or start pm2 by itself, so do it in this order:

1. **[repo owner]** Delete the variable (Settings → Secrets and variables → Actions → Variables → `DOCKER_DEPLOY_ENABLED` → delete) and wait for any Docker deploy that is running to finish (they never overlap).
2. **[server]** Roll back the server: section 9, steps 1 to 6 (stop the container, copy the newer uploads back, verify, `pm2 start onboarding-backend`, check the site; there is no proxy to switch).
3. The next push to `main` deploys with pm2 again. Push a small change and confirm that `Deploy Backend` ran and `Deploy Backend (Docker)` did not.

### Not verified

The workflows cannot be run until the variable is `true`, so the first real run is the test. What was checked before: the workflow files are valid, every action they use exists, the CI `docker` job (image build, health, commit, graceful stop) passes, and `scripts/deploy-docker.sh` has been run only against a laptop's Docker (`docker-proof.sh`), not on the VM.

## 12. Decisions and limits

- **MongoDB stays on Atlas** (`MONGODB_URI`). It is not containerised for production; the dev compose file has its own MongoDB for local work only.
- **Uploads stay on local disk** (a volume). Moving them to object storage is a separate, later plan.
- **Memory and CPU limits:** see section 6. The defaults in the compose file are a guess from reading the code.
- **Client IP:** the app trusts `TRUST_PROXY_HOPS` proxies (default 1) and, separately, an `x-client-ip` header only when `x-proxy-secret` equals `PROXY_SHARED_SECRET` (the frontend's own proxy). If the container's port were reachable from the internet with the default of 1, a caller could forge their address with `X-Forwarded-For` and sidestep the rate limits. That is why the compose file publishes the port on `127.0.0.1` by default; on this VM, where nothing runs in front and the forwarder reaches port 5000 directly, `BIND_ADDRESS=0.0.0.0` is set at the cutover, with `TRUST_PROXY_HOPS` set to the number of proxies between the visitor and the VM (read it from the live `.env` before the cutover and keep the same value).
- **Shutdown:** SIGTERM stops new connections, lets requests in flight finish for up to 25 seconds, closes the database connection and exits 0 (Docker waits 30 seconds before it kills).
- **Not verified here:** the image was written on a machine without Docker. The build, the container checks in `scripts/docker-proof.sh` and the CI job `docker` have to run before the first real deploy. The base image is pinned by tag; pin it by digest after the first build.
